# Передача и самостоятельный запуск

## Срок и ответственность

Старое размещение работает до **21 ноября 2026 включительно, Asia/Yakutsk,
UTC+9**. С 22 ноября получатель отвечает за размещение и поддержку.
После передачи сопровождение, консультации и повторные выгрузки прежним
владельцем не предусмотрены. Получатель выполняет перенос самостоятельно.
Срок фиксированный, даже если перенос не завершен. Документ не запускает
автоматическое отключение. В установленную дату владелец отдельно остановит
frontend, отзовет проектные доступы; удаление облачной базы только после
проверки последнего полного архива.

## Что получить

1. Полный код из публичного репозитория; копировать в собственный аккаунт.
2. Зашифрованный файл `.sabai`, пароль отдельно. В нем SQL базы, роли,
   функции/RLS, данные с deleted_at, аудит/снимки, app_state, Auth, история
   миграций, Storage-файлы с путями и manifest с контрольными суммами.
   Также project/ с автономной копией кода, source-history.bundle с исходной
   историей Git и private/source-export.env с временными проектными доступами.
3. Версию кода (commit), дату архива и результаты сверки. Предварительная
   выгрузка при работающей студии не заменяет финальный backup.

Личные management-токены, Google client secret, папку .vercel и локальные
служебные файлы не переносить. По решению владельца публично размещается
только зашифрованный архив. Пароль передавать отдельным приватным каналом,
не в README, GitHub Issues или Release. Контакты клиентов
и Auth-данные являются чувствительными данными.

## Расшифровка

Node 24, Docker, Supabase CLI, tar; для ручного облачного восстановления также
Postgres-клиент совместимой версии (17 или новее).

```bash
HANDOVER_PASSWORD_FILE=/private/password.txt node scripts/handover/archive.mjs decrypt /private/sabai-clay.sabai /private/payload.tar.gz
mkdir -m 700 /private/restored
tar -xzf /private/payload.tar.gz -C /private/restored
node scripts/handover/verify.mjs /private/restored
```

Распаковывать только после успешной проверки аутентификации AES-256-GCM.
Не заменять полный архив Excel-отчетом. В manifest находится SHA кода на момент
экспорта и список локальных изменений, если backup сделан до commit.
После приемки убрать временные расшифрованные копии из общих папок и облачных
синхронизаций. Копия с паролем не должна находиться в том же канале передачи.

Полный код находится в project/ и доступен без повторного скачивания GitHub.
Исходную историю при необходимости открыть только локально или в приватном Git:

```bash
git clone /private/restored/source-history.bundle /private/source-history
```

В истории могут находиться прежние данные и реквизиты; не подключать ее к
публичному remote. Публичный репозиторий специально начинает новую историю,
а исходная целиком сохранена в зашифрованном комплекте.

## Свежие данные без прежнего владельца

private/source-export.env содержит только реквизиты этой студии: project ref,
административное Postgres-соединение и Storage service-role. Они дают широкие
права на данные этого проекта: использовать только для чтения и переноса,
не менять работающую студию. Доступа к другим проектам, личным аккаунтам,
биллингу, Supabase Dashboard или Google Cloud этот файл не дает.

Проверить доступ и сделать собственную полную выгрузку (Node 24 и Docker):

```bash
node --env-file=/private/restored/private/source-export.env scripts/handover/export.mjs --check-access
node --env-file=/private/restored/private/source-export.env scripts/handover/export.mjs
```

Общий Supabase management-токен не требуется. Provider secrets не выгружаются:
для своего размещения получатель создает собственный Google OAuth. Не добавлять
source-export.env в Git, не вставлять реквизиты в чат Codex, frontend или .env.local.
Скрипт читает их из файла. Новая выгрузка и новый пароль остаются локально в backups/;
проверить расшифровку и восстановление, не публиковать пароль рядом с архивом.

Временные реквизиты не имеют самостоятельного автоматического срока истечения.
Старые сервисы отключаются и проектные доступы отзываются после 21 ноября
по решению владельца. Получатель обязан завершить перенос заранее; дата
не продлевается. После переключения пользоваться только своим облаком и ключами.

## Собственные сервисы

Создать Supabase у получателя, с совместимой версией Postgres и достаточной
квотой Storage. При переносе полных данных использовать SQL архив, а не
supabase/schema.sql и не старый импорт. Перед восстановлением убедиться, что
назначение пустое; никогда не подставлять старый source URL в команды восстановления.

Следовать [официальной процедуре backup/restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).
CLI экспортирует только пользовательскую схему, а управляемые auth/storage
создаются самим Supabase. Полный дамп данных может содержать служебные строки:
сравнить версии Auth/Storage, не импортировать несовместимые migration records.
Auth-пользователей/identities сохранить; старые сессии при переключении отозвать.
Прежние OAuth provider secrets и ключи подписи не переносить: сотрудники входят заново.

Основной SQL порядок (psql, ON_ERROR_STOP и единая транзакция):

```bash
node scripts/handover/prepareRestore.mjs data.sql /private/data-restore.sql
psql "$TARGET_DATABASE_URL" --single-transaction --set ON_ERROR_STOP=1 \
  --file roles.sql --file schema.sql \
  --command 'SET session_replication_role = replica' --file /private/data-restore.sql --file audit.sql
psql "$TARGET_DATABASE_URL" --set ON_ERROR_STOP=1 --file auth-storage-policies.sql
```

**До запуска** просмотреть roles.sql: системные роли управляются платформой,
не перезаписывать их пароли. `session_replication_role=replica` разрешен только
административному соединению и только при восстановлении; не применять к работе
приложения. Не запускать restore повторно поверх данных. Историю миграций из
отдельных файлов восстанавливать после проверки существующей таблицы истории.

prepareRestore сохраняет исходный dump и исключает из рабочей загрузки метаданные
Storage и временные Auth-сессии/токены. Пользователи и identities переносятся,
сотрудники входят заново. Storage API ниже создаст новые метаданные для исходных
путей. Не копировать data.sql напрямую: иначе появятся записи objects без файлов.

Storage metadata и файлы разные вещи. Восстановление SQL не восстанавливает фото.
Создать buckets по архиву и загрузить файлы через Storage API, сохраняя bucket/name
из storage-objects.json. Использовать новый административный ключ только в
локальном скрипте получателя. Не вставлять напрямую строки objects вместо
загрузки файлов: метаданные должен создать Storage API. Проверить размер и SHA256.
Приложение строит URL фото из своего настроенного Supabase и старого path,
поэтому старый сохраненный url не является источником адреса.

После проверки SQL использовать защищенный от записи в исходный проект скрипт:

```bash
HANDOVER_TARGET_URL=https://NEW_PROJECT_REF.supabase.co HANDOVER_TARGET_SERVICE_KEY=... node scripts/handover/restoreStorage.mjs /private/restored
```

Скрипт не перезаписывает существующие файлы, допускает повтор только при совпадении
байтов и проверяет SHA256 скачанного из нового Storage файла.

## Google и роли

В собственном Google Cloud создать OAuth web client. В Google разрешить
callback `https://НОВЫЙ_PROJECT_REF.supabase.co/auth/v1/callback`.
В Supabase Auth включить Google со своими client ID/secret; задать Site URL
нового frontend и Redirect URLs для его адреса и нужных локальных тестов.
Никогда не помещать Google secret или service-role в VITE-переменные.

В Supabase SQL Editor назначить получателя администратором:

```sql
insert into public.staff_profiles (email, display_name, teacher, role, is_active)
values ('RECEIVER_EMAIL', 'Администратор', 'Другое', 'admin', true)
on conflict (email_normalized) do update
set display_name = excluded.display_name, teacher = excluded.teacher,
    role = excluded.role, is_active = true;
```

Для сотрудников role = teacher, teacher = Алина / Настя, display_name =
нужное отображаемое имя. После переноса деактивировать прежнего администратора
в новой базе. UI-привилегий по захардкоженному email нет; профиль нужен и в базе.
Auth-вход без staff_profiles не дает права менять данные.

Часть CRM и фото публично читается, memberships/guest_masters ограничены
сотрудниками. Это существующая модель, а не приватный портал. Ужесточение чтения
отдельная задача с тестированием RLS; не обещать конфиденциальность по одной
скрытой кнопке. Перед передачей проверить фактические pg_policies в архиве.

## Frontend

В чистом клоне npm ci. Создать .env.local из .env.example с **новыми** URL/key.
Для Vercel создать собственный проект из своего GitHub: Node 24, Vite, npm ci,
npm run build, dist. Задать свои переменные в Production и Preview. Не копировать
.vercel автора. Для любого другого статического хостинга HTTPS, MIME и fallback
index.html; переменные встроены в сборку, изменения требуют новой публикации.

В DevTools Network отфильтровать supabase: все запросы и фото должны идти
только в новый project ref. В OAuth проверить новый callback. У старой и новой
базы разный localStorage namespace, старый writable-кэш не импортируется.

## Приемка и переключение

1. Проверить чистую установку схемы на изолированном локальном Supabase и отдельно
   восстановление архива. Сверить количество строк каждой public-таблицы, включая
   deleted_at, Auth users/identities, пути/число/хеши фото, абонементы/сертификаты.
2. Сверить месячные доходы/расходы/прибыль по financeMetrics, не только общий баланс.
3. Проверить вход всех сотрудников, нового админа, read-only гостя, запись и
   редактирование, расход, фото, списание/возврат абонемента, Excel.
4. Проверить 390 px, Safari/PWA на реальном iPhone. Старый белый экран считать
   незакрытым до проверки на устройстве, где он наблюдался.
5. Согласовать короткую паузу ввода. Закрыть рабочие вкладки старого приложения,
   дождаться сохранений, самостоятельно сделать **свежую** полную выгрузку и
   проверку восстановления с помощью переданного проектного доступа.
   Не сливать две активно изменяемые базы задним числом.
6. Только после сверки сотрудники переходят исключительно на новый адрес.
   Раздать новый PWA URL и удалить/заменить старую иконку с экрана Домой.

## Последний архив и отключение

Получатель до конца 21 ноября самостоятельно сохраняет свежие изменения и
проверяет восстановление. Прежний владелец не готовит повторный архив при
отключении. После переключения backup своей базы организует получатель.
Прежний владелец останавливает старый frontend и отзывает проектные доступы,
не затрагивая учетные записи и ресурсы других своих проектов. Удаление исходной
базы допускается после проверки переданного полного архива. Дату не продлевает
неготовность получателя.

## Повторная административная выгрузка

```bash
node --env-file=/private/restored/private/source-export.env scripts/handover/export.mjs
```

Личные management-токены не требуются. DATABASE_URL содержит административное
соединение; при проблеме IPv6 использовать
session pooler порт 5432. Аудит выгружается ограниченными диапазонами ID в audit.sql.
Скрипт использует штатный Supabase CLI, сохраняет данные отдельно, не делает
business writes. Проверяет полноту скачивания Storage, пишет counts/checksums,
шифрует. Для финальной копии обязательна пауза ввода: одинаковые counts не
доказывают отсутствие изменений значений во время выгрузки.

  включая мягко удаленные записи, платежи, расходы, абонементы и сертификаты.

- В Storage перенесены все исходные файлы, SHA256 скачанных копий совпали.
  Отсутствующих путей в связях с фото не обнаружено.

  запись и изображение остались после перезагрузки и читаются из нового Storage.
- WebKit с эмуляцией iPhone 390 px: запуск, нижняя навигация, отсутствие
  горизонтального overflow и ошибок консоли. Исправлен выход меню за край при
  нулевом safe-area. Эмуляция не заменяет приемку на физическом iPhone/PWA.
- Старый пользовательский черный/белый экран не воспроизведен; считать случай
  незакрытым до проверки исходного устройства. Настоящий Google-вход с новыми
  OAuth реквизитами проверяется уже в сервисах получателя.

Исторический Excel seed удален из текущего дерева. Публичный репозиторий имеет
новую историю без него. **Исходная история в source-history.bundle его содержит**;
bundle и распакованную копию сохранять приватными.

На дату проверки npm audit сообщил 9 проблем зависимостей (включая dev).
В production-наборе известен high для xlsx 0.18.5: prototype pollution и ReDoS.
Приложение использует библиотеку для формирования отчета; старый импорт Excel
заблокирован. Это не устраняет все риски зависимости. Планировать замену/обновление
отдельно с повторной проверкой отчетов, не запускать npm audit fix --force вслепую.
